# Configurator development

Read this for work on `packages/configurator/`. User-facing setup and API documentation start in the [package README](../packages/configurator/README.md). The [Vite guide](./vite-plugin.md) owns bundler integration and packaging; [library internals](./tailwind-merge-internals.md) own the merge engine and shared CI guardrails.

## Goals and strategy

The configurator bridges Tailwind's build-time knowledge and tailwind-merge's runtime classification. A custom font size such as `--text-huge` should not need a hand-maintained merge configuration, and namespace resets, compat sub-namespaces, prefixes, and custom utilities should follow the project's CSS.

- Derive theme-specific knowledge from Tailwind's resolved design system. Keep class-group semantics and conflicts in `default-config.ts` as the single maintained skeleton; do not create a parallel utility-to-namespace table.
- Preserve classification of real theme classes. Compact encoding may overmatch finite scales for size; exact encoding avoids that tradeoff for named values. Both need explicit classification and merge gates, not just comparison with the default config.
- Keep browser work small: emit a normal config for `createTailwindMerge`, preserve lazy initialization and composability, and avoid importing the default config in the emitted module. Tailwind and scanner dependencies remain build-time only.
- Keep the library API as the reusable core. CLI and bundler integrations should own their I/O, logging, watching, and failure policy while reusing generation and scanning. Do not implement a bundler feature by invoking the CLI.
- Keep build-time internals outside the library's stable API. The configurator uses the explicit `tailwind-merge/unstable-do-not-import` entry for classification and parsing; consuming it requires a compatible library release. A shared internal runtime package remains a possible later split, not a prerequisite for this integration.
- Prune only as an optional optimization of a complete generated config. The invariant is identical merging for lists composed of supplied candidates, not a strict allowlist and not a stronger correctness guarantee than the full config.
- Measure compressed bundle size as well as minified size. A smaller source representation can compress worse; keep the [measurement methodology and baseline](./configurator-performance.md) when evaluating alternatives.

Non-goals remain runtime discovery from DOM/computed CSS, parsing compiled output as a complete theme, direct v3 JS-config input, and a separate merge engine. Compiled CSS omits unused variables; a custom runtime would duplicate the library's parser/conflict/performance work for little measured gain. Legacy configs work through `@config` in v4 CSS. Separate generated modules can describe separate themes; a single function does not infer which theme a caller intended.

## Pipeline and ownership

All source paths in this table are relative to `packages/configurator/src/`.

| File | Responsibility |
| --- | --- |
| `generate.ts` | Loads project and vanilla systems, builds plans, applies custom utilities, augments/corrects class claims, detects modifier ordering, optionally prunes, then materializes and emits. |
| `design-system.ts` | Thin Tailwind API adapter, memoized class lists, prefix-aware compilation, and style-scope annotation of PostCSS declarations. |
| `property-coverage.ts` | Known CSS shorthand relationships and the default config's logical-axis coverage policy; shared by inference and the test oracle. |
| `snapshot.ts` | Normalizes theme entries and prefix; compound theme keys do not become standalone scale values. |
| `plan.ts` | Walks `getDefaultConfig()`, resolves theme getters via `themeKey`, copies scales per group, removes disabled members, and carries group/conflict/modifier ordering. |
| `compress.ts` | Chooses enumeration, validators, or nested prefix families under the selected encoding policy. |
| `custom-utilities.ts` | Compares utility registries, classifies aliases, and derives self-conflict groups and directional override edges. |
| `augment.ts` | Diffs named classes against vanilla, classifies extra namespaces, probes alternative spellings, and resolves competing claims. |
| `prune.ts` | Uses the library parser/classifier on the completed config, then retains reached members and live conflict edges. |
| `materialize.ts`, `emit.ts` | Produce the in-memory config and generated TS/JS from the same plan. |
| `scan.ts` | Compiles source configuration, collects dependency files and safelists, and wraps oxide scanning. |
| `css-statements.ts` | Shared lexical inspection of active CSS statements and block headers, plus bracket/quote-aware segmentation for scanning and utility probes. |
| `resolvers.ts` | Shares Tailwind-compatible stylesheet/module resolution, records stylesheet roles independently of extensions, and collects missing targets and failed local module graphs for recovery. |
| `run-cli.ts`, `cli.ts` | Argument parsing, file I/O, source scanning, report output, and full-content `--check`. |

Project and vanilla loads use the same `@tailwindcss/node` compiler and CSS-resolution base. Do not substitute a globally installed vanilla baseline. The compiler itself comes from the package's dependency resolution; resolving CSS imports from the project does not guarantee compiler-version equality with another integration.

Inspect variant selectors after utility classification and augmentation, but before pruning the completed plan. Tailwind's selector inspection populates its parsed-variant cache, and `candidatesToCss()` rebuilds variant ordering from that cache on every call. Inspecting all variants first makes each utility probe repeat that sorting work; profiling the Supabase fixture identified it as the CI timeout bottleneck. Keep the pass ordering explicit instead of caching Tailwind's mutable variant state or reducing probe coverage. See the [performance reference](./configurator-performance.md#generation-profiling-2026-09-07).

PostCSS parses compiled declarations; keep only target/condition interpretation in `design-system.ts`, rather than maintaining another CSS lexer. It handles escaped property names, importance, comments, quoted punctuation, and balanced custom-property values. This is a build-time dependency, declared by both the configurator and the Vite package that bundles its source. The lightweight `cssStatements` reader intentionally remains separate: root discovery must still recognize an entrypoint during an unfinished edit, before its CSS can be parsed successfully. Tailwind owns validation and the normal generation failure/recovery path. Candidate/value `segment` also stays separate because it splits Tailwind class syntax, not stylesheets.

Bundlers can pass `TailwindIntegration` resolution/dependency hooks to generation and scanning. Both resolvers are optional, so dependency-only integrations still use the observable loaders with normal filesystem resolution. The node wrapper's design-system loader currently drops resolver hooks, so `design-system.ts` uses its underlying Tailwind engine with explicit stylesheet/module loaders when an integration is supplied. Resolve that engine from the installed node package, never from the project or a mutable global resolver hook. Aliased JavaScript paths must be passed back to node's `loadModule` as relative requests: only that path captures transitive dependencies and refreshes ESM imports. Scanning also passes the hooks to `compile()`; otherwise imports, source directives, and generation can describe different projects.

A resolver returning `false`/`undefined` declines the request rather than rejecting it. The shared stylesheet resolver mirrors Tailwind's enhanced-resolve settings (style fields/conditions, CSS extension defaults, and NODE_PATH) for fallback, including explicit `.pcss` and extensionless paths. The node package does not export its stylesheet loader/resolver, so enhanced-resolve is an explicit dependency rather than an import through a transitive dependency's private path. Record stylesheet roles at resolution time; suffix filtering loses inline sources, while parsing every dependency as CSS can interpret JavaScript template strings as directives.

The stylesheet resolver deliberately uses a fresh resolver with uncached `fs` instead of Tailwind's shared cached filesystem. This keeps newly created or repaired imports visible across regeneration attempts without another invalidation mechanism. Revisit only if measurements identify resolution as a bottleneck, and preserve retry correctness if introducing a cache. Bundler CSS results can be alias-expanded requests rather than complete filenames; always finish their filesystem/package resolution here. Otherwise an extensionless alias either bypasses `.css` lookup or reports missing paths under the original package-like name instead of the aliased directory.

On failed stylesheet resolution, forward enhanced-resolve's `missingDependencies` to the integration dependency callback. These attempted paths let a watcher recover when a missing import is created, including outside the project root and with implicit `.css` resolution. Report them separately from resolved stylesheet roles: resolver metadata such as a missing `package.json` must never enter safelist parsing. Failed local CSS/module requests also report their closest existing parent directory, since Rollup's watcher can miss creation when several missing filenames share a directory. Choose that directory from the actual alias-expanded request, never from ancestor metadata attempts. Callbacks can therefore report files, missing paths, or recovery directories. Successful resolution does not report failed alternatives or recovery directories.

JavaScript resolution uses the same fresh-filesystem and missing-dependency mechanism, with Tailwind's module extensions and import-then-require conditions. Apply it in both design-system loading and scanning. Record resolved configs/plugins before execution can fail, and pass the resolved file back to node's `loadModule` through its resolver callback; otherwise its cached filesystem can reject a just-created module even though our fresh lookup succeeded. Keep relative loader requests for dependency collection and ESM invalidation. Regressions exercise creation-only recovery for `@config` and `@plugin`, aliases, out-of-root files, and both pruning modes, plus package condition precedence and fallback.

Tailwind's `loadModule` reports transitive dependencies only after both execution and its import walk succeed. On execution failure, the design-system adapter must await `trackModuleDependencies` before rethrowing: it follows literal local imports/re-exports/requires, records resolved and missing children, and tolerates broken syntax and cycles. The collector only adds recovery watches; it never executes JavaScript or replaces the loader's error, and it stays off the successful path. Like Tailwind's collector, it does not evaluate computed import specifiers or traverse bare package imports. The permissive import patterns may over-watch quoted/commented examples, but must not greedily skip a real import in favor of a later `from` clause. Tests pin directory package entries, JS/TS extension preference, missing grandchildren, and creation/repair of transitive configs/plugins in a real Vite server.

The plan references validators by name and holds class groups/conflicts in ordered maps. Only public validators can be serialized. Each group's scale is independently copied so collision corrections cannot remove another group's members; the emitter recovers shared scale runs structurally.

## Classification constraints and regression lessons

- Class-list suggestions are unprefixed. Keep classifiers unprefixed, and apply the configured prefix centrally when sending candidates to Tailwind in `declaredDeclarations` or `classesCompile`. Earlier unprefixed probes under a prefixed theme silently skipped every augmentation and custom-utility inference while simple namespace tests stayed green.
- A changed class claim must be checked against compiled declarations. A theme color called `xl` may own `text-xl` while `drop-shadow-xl` remains a size; `bg-bottom` can represent multiple effects. Correct the owning group's copy, or neutralize all claims when removing the class would lose independent effects. Preserve report entries and ordering through pruning.
- Neutralize combined effects for newly suggested names too. Absence from vanilla's class list does not imply absence from its matchers: `--color-x-13` makes `border-x-13` and `divide-x-13` colors as well as widths already matched by numeric validators. Consult the vanilla classifier to remove or outrank that underlying claim alongside the project claim; removing only the color exposes the width again. Names with no vanilla matcher still need their project claim removed. Regressions cover numeric and named widths, both axes, encodings, prefixes, pruning, and emitted modules while ordinary color and width uses keep merging.
- Matching project/vanilla group IDs do not prove that an existing class kept its meaning: `--text-color-base` turns `text-base` into color while its old font-size matcher still wins. Compare `utilities.getCompletions(root)` branch membership before `getClassList()` deduplicates names, then recheck affected classes against compiled properties. A uniquely identified new owner needs an explicit assignment as well as removal of the old claim. Combined effects must be neutralized even when the old and claiming group IDs are identical; deduplicate those IDs before removing claims. Keep custom-utility groups out of this pass. Compiling the entire vanilla class list on every generation was measured to add several seconds; grouped suggestion differences avoid that cost without a separate namespace table.
- Tailwind's suggestion list omits some compiling aliases. Augmentation probes a group's other spellings and accepts aliases with byte-identical declarations; do not replace that with a hand-maintained alias table.
- Static custom aliases must match exactly one built-in signature and cover each other's effects. A base color plus a hover/dark color cannot alias an unconditional color, even though their property-name sets match. A later custom class may remove another group only when it fully covers all its declarations. Built-in-to-custom edges are not inferred generally. Conditional/pseudo-element declarations may only be shared identical scaffolding, including their full enclosing rule paths, and custom-property state must be covered as well. `DeclarationEntry.scope` preserves those headers relative to the utility selector; compare with `sameDeclarationScope`, not the `conditional` flag alone. Conditions are compared conservatively as text, without logical equivalence inference.
- Declaration parsing must handle quotes, escapes, and balanced value blocks before interpreting style braces or semicolons. Custom properties can contain blocks such as `--state: {ready}` with nested braces, brackets, parentheses, and semicolons; these do not open style scopes or end declarations. Losing those declarations can turn a combined utility into an unsafe base-color alias. Regressions cover escaped quotes/backslashes, following declarations and real nested styles, both encodings, prefixes, emitted configurations, and pruning. Inspect `candidatesToCss()` to distinguish parser defects from upstream output changes: Tailwind 4.3.3 itself truncates a block value containing nested `!important`, before our parser sees it.
- Custom-property names follow CSS identifier rules, including digits and underscores after `--`, non-ASCII characters, and CSS escapes. Match the declaration's property and delimiter together so an escaped colon remains part of the name. Losing this state can alias a utility to a color group even when another class reads its variable.
- Preserve declarations under style grouping rules such as `@starting-style`, `@scope`, and `@layer`, retaining their full scope and marking coverage conditional. Skip only known non-element blocks (`@property` and keyframes, including vendor-prefixed keyframes); an unrecognized wrapper must not silently erase independent effects and enable unsafe aliasing.
- Keep declaration importance separate from the value in `DeclarationEntry.important`. Coverage requires the coverer to be at least as important as the target, including shorthand/longhand relationships, conditional declarations, and custom-property state. An inline-important color cannot join the normal `text-color` group because normal colors cannot cover it in return. Equality checks in augmentation must compare importance too; a class-name important modifier is a separate runtime concern.
- Augmentation must preserve the groups established by custom-utility inference. Names such as `text-special` or shadcn's `border-grid` resemble built-in roots, but reclassifying them by property signatures alone would undo the conditional alias guard. Pass the custom group's identity through the pipeline rather than infer ownership from its name.
- Custom functional classes are indexed once by their longest functional root, with exact bare utility names excluded. Resolve ownership against the entire project registry, including built-ins: `flow-root` is not a value of custom `flow-*`; `backdrop-blur-sm` belongs to built-in `backdrop-blur-*`, and bare functional defaults such as `backdrop-grayscale` keep their own roots too. Encoding and conflict exemplars share that ownership rule: using the first `startsWith(root + '-')` suggestion can infer unrelated conflicts. Keep each group's exemplar beside its members instead of reconstructing roots from group IDs.
- A failed child trie lookup retries ancestor validators. Compact custom roots with registered descendants therefore use exact-mode value matchers, even when the parent has uniform effects: `isAny` would reclaim a deliberately unclassified child, including an unsupported arbitrary branch of a mixed-effect root. Normalize registry roots to the runtime's unsigned paths before checking ancestry. Test preserved children against both numeric and named parent values, with prefixes, pruning, and emitted modules; the parent's own supported classes must still merge.
- Do not assume every value of a functional root sets the same properties: Tailwind removes each declaration whose `--value()` cannot resolve. Group named values and accepted bare numeric kinds by compiled property, scope, and importance. A `text-stroke-*` width branch must coexist with its color branch; a numeric color token can set both. Mixed-effect roots enumerate names even in compact mode and omit broad arbitrary/variable matchers, preserving those classes conservatively. Probe arbitrary kinds when detecting mixed effects even if only one branch has suggestions, and keep integer validators ahead of number validators when their effects differ. A bare static default joins its functional group only when the root has one observed effect shape and mutual coverage holds. Regressions cover both encodings, prefixes, emitted round trips, and pruning.
- Base-value and slash-modifier probes share the same arbitrary data-type samples. Omitting images, ratios, or another accepted kind can make independent branches appear uniform and grant an unsafe `isAny`/`isArbitraryValue` matcher. The regression matrix exercises every currently supported type with different samples from the probes, checks mixed named/arbitrary effects, and keeps uniform roots merging in exact mode. Use bracket-aware `segment` when detecting an existing postfix: the slash inside `[5/4]` or a URL is part of the base value, so that base still needs modifier probes.
- Register mixed functional groups in `postfixLookupClassGroups`. A postfix can add independent effects (`pair-2/3` has width and height while `pair-2` has only width); default runtime lookup strips the suffix before classification unless the base group requests full lookup. Include each class-list suggestion's named modifiers when collecting functional candidates, and collect root-level modifiers independently through `utilities.getCompletions(root)`. Numeric/arbitrary-only roots can have modifier suggestions but no class-list entries at all. Probe those named modifiers on the base samples too; if their independent effects lack a safe full-class matcher, preserve the root. Deduplicate complete candidates and modifier probes without dropping suggestions from repeated branches, and retain longest-root ownership before expanding class-list candidates. The group split alone does not preserve those effects. Pruning must use the same full-class lookup.
- Static utility names containing `/` need the same lookup registration, including aliases of built-in groups. After augmentation finishes, resolve each static class and its base against the final plan and register the base group when they differ. Do not infer the base's owner from custom group IDs: it can be an alias, a built-in matcher, or a class augmentation only just added. Use the runtime parser for the postfix boundary and unprefixed registry names; register before pruning so the base matcher survives even when only the slash class is scanned. Regressions cover independent custom groups, aliases, built-in/augmented bases, ordinary numeric/opacity/fraction modifiers, prefixes, and emitted/pruned configurations.
- Probe both bare numeric and arbitrary slash modifiers on named and probed base values, covering Tailwind's recognized data types (including ratios, images, font sizes, angles, and vectors). Tailwind can provide no suggestions for `--modifier(number)`, `integer`, or `percentage`; use integer percentages in bare probes because decimal percentages do not compile. A full-lookup miss still falls back to the base group, so omitting only an unknown postfix matcher is unsafe. When a modifier changes the effect signature, require the full class to resolve to that effect group through emitted names or validators in runtime precedence order. Fractions can represent numeric pairs but not a named base such as `type-sm/2`. Otherwise leave the root unclassified in both encodings, keep its suggested classes out of augmentation, and report them as unassigned. This intentionally preserves even redundant base classes. Uniform effects and representable split groups retain merging. Regressions cover bare numeric kinds, every arbitrary data type, arithmetic inside postfix brackets, arbitrary bases, built-in-like names, prefixes, emitted modules, and pruning; revisit the type matrix when updating Tailwind.
- Infer additional order-sensitive modifiers from added/redefined variant selector templates and their suggested named values. Compile candidates to detect changes to the styled target; media-only and ordinary element-state conditions commute, while selector lists are conservative barriers because they can mix targets. Open custom variant spellings absent from suggestions remain a documented extension case. A numeric variant's CSS hexadecimal escape can consume a trailing space (`\33 xl`); that space is part of the escaped class name, not a descendant selector.
- The declaration oracle is directional: a longhand after a shorthand does not replace the whole shorthand. Identical declarations and `var()`-carried state can compose. Keep CSS facts in `property-coverage.ts` as explicit shorthand relationships, including reset-only longhands; never infer them from prefixes or inserted name segments. Unknown relationships preserve classes. `font` resets line height and variant properties but excludes synthesis; `border-width` excludes `border-image-width`, while the whole `border` resets border images. Border and side shorthands exclude radii, while `border-radius` covers physical and logical corners. The expanded map also preserves the library's horizontal-tb axis policy without equating individual logical and physical sides. Test this map independently because generation and the declaration oracle share it, and include retained styles as well as real shorthand overrides in emitted/pruned merge regressions.
- Normalize negative custom roots to the runtime's unsigned trie key. Opposite functional roots can share a group only when both are uniform and mutually cover their effects; otherwise preserve both roots, including their normalized suggested names during augmentation. Compare opposite static registrations too, even when no custom functional root exists, and use the normalized preserved name to skip both aliases and self-conflict groups. A compatible functional root must not re-register a preserved static name as its bare default. Check positive custom static names under the same lookup path before assigning aliases or self-conflict groups, and compile their actual negative spellings even when they are absent from suggestions. Preserve the static claims together with incompatible functional roots: keeping either claim can still classify both signs. Compatible static names can retain merging. Keep actual signed names for compilation and use the already compiled shape exemplar for conflict inference, including roots with no named suggestions. Test both signs, negative-only roots, static aliases and multi-property statics, importance, named/numeric values, prefixes, emitted modules, and pruning.
- An overmatched nonexistent name still has eviction power. Exact mode enumerates finite names and probes open custom value kinds; arbitrary-value validators still approximate types. Do not promise that exact mode validates every possible CSS value.

## Emission and pruning decisions

`getConfig` constructs the config lazily and exports a fresh object per call; emitted `twMerge` uses `createTailwindMerge(getConfig)`. The emitted `theme` is empty because scales are materialized into groups. TS uses `satisfies`; JS is transform-free ESM. `generate` exposes `format` and `importSource`, but the emitter's internal `sharing` modes are not public API options.

Validators become local bindings so minifiers can rename them. Default sharing hoists theme scales; aggressive structural sharing remains an internal measurement option because extra references can worsen gzip/brotli. Formatting is fixed and deterministic, not inherited from the host project's formatter. CLI banners hash the entrypoint text, not the import graph; full-content regeneration makes `--check` detect dependency changes anyway.

Serialize `__proto__` object keys with computed syntax (`['__proto__']`); an ordinary or quoted object-literal key sets the prototype instead of preserving a theme family. Keep key serialization shared by inline objects, hoisted structures, and record maps. Regression tests execute TS and JS modules under every sharing mode and both encodings, with and without pruning, and compare their config and merge behavior with the materialized result.

Pruning runs after custom utilities, augmentations, and collision correction. Use the library's unstable `createClassGroupLookup` to observe each candidate through the real merge engine; do not recreate its modifier/postfix decision tree in the configurator. The tooling wrapper records successful lookups without changing the runtime hot path. Preserve trie precedence and keep every validator reached by a used candidate. Retain every successful lookup step, including the base matcher that enables a slash-modified class to resolve into a different final group. Keeping only the final group can promote a broader validator that bypasses postfix lookup. Count each supplied candidate once in the pruning report even when it retains several groups. If member attribution cannot explain a classifier hit, retain the whole group and report it in `unprunedClassGroups`. Validators may retain more than the scanned names; this is intentional conservative behavior.

Use oxide over Tailwind's source configuration, not Vite's module graph: raw template/Markdown files and external `@source` packages may never enter that graph, and client/server graphs differ. `compile()` supplies roots, source entries, features, and dependency callbacks. Inline candidates are private upstream, so `scan.ts` parses active CSS statements from the entrypoint and CSS dependencies and ports Tailwind's brace expansion, including negations. Preserve comment/string boundaries: a regex over raw CSS can make a commented exclusion remove a class Tailwind still emits. Scanner regressions check emitted Tailwind CSS and pruned merge behavior for both entrypoint and imported directives. Recreate the scanner when the CSS graph changes; reuse it for source-only edits. The direct API and CLI propagate scan errors; the Vite wrapper may fall back to the full config.

## Debugging and validation

The test paths and bare inspector command below are relative to `packages/configurator/`. Prefer new cases in existing fixtures before adding a whole new theme; expensive generation should be shared. The [real-world fixture README](../packages/configurator/tests/fixtures/real-world/README.md) is permanent provenance and refresh guidance, not disposable research material.

`effect-combinations.test.ts` checks pairs and triples of known independent longhands with expected coverage derived from the fixture's property sets, not production declaration/coverage helpers. It combines those cases with preserved custom roots, signed/static slash collisions, theme collisions, variants, and importance across both encodings, prefixes, pruning, and emitted TS/JS. Keep an independent expectation layer like this alongside the larger conformance oracle, since that oracle shares production helpers and can agree with the same bug.

- The configurator's correctness gates are helper assertions in `packages/configurator/tests/fixture-utils.ts` (`assertTailwindConformance`, `assertExactClassificationParity`, `assertPruningEquivalence`, and the table helper `expectMerges`); tests that only call them are whitelisted for `vitest/expect-expect` in the package's eslint config — extend that list when adding a gate. The conflict oracle behind the sweeps lives in `tests/oracle.ts` (`mergeVerdict`: directional, var()-composition-aware; see its doc comment before changing verdict rules) and is importable under plain Node, which `scripts/explain.mts` relies on.
- `generateFixture` is memoized per CSS/base/options within a worker and runs every emitted module through a round trip (written to `tests/.tmp-roundtrip-*`, imported through Vitest, `getConfig()` deep-equal to the materialized config). Cost scales with the number of distinct fixtures (0.1–1 s each), not with assertions — add cases to existing fixtures first; a new theme only for a new theme shape. Use `expectMerges` for curated tables (every mismatch reported at once, input and output side by side) and `mergeTable` + `toMatchInlineSnapshot` for exploratory batches.
- Load large theme fixtures when their tests run, not through eager promises created inside `describe`. This assigns generation cost and failures to the relevant theme instead of making the first test wait behind unrelated generations. Lazy loaders still share generated fixtures through `generateFixture`'s cache; profile an individual slow generation before changing test timeouts.
- `tests/vanilla-coverage.test.ts` is a ratchet against Tailwind itself (unclassified classes, consecutive pairs, cross-group exemplar pairs) with file snapshots of known divergences under `tests/__snapshots__/vanilla-coverage/`. Those lists name tailwind-merge default-config gaps as much as configurator ones; a new line after a change is something to look at, a removed line is a fix — update the snapshot deliberately, never blindly with `-u`. Divergences the library keeps on purpose (grid `col-start`/`col-end` before `col-span` per tailwind-merge#176, `sr-only` as a toggle) go into the file's `INTENTIONAL_DIVERGENCES` allowlist with a reason instead of the snapshots; a companion test fails when an allowlisted pair stops diverging, so stale entries get removed. The oracle itself stays a pure statement about compiled CSS — never encode library policy in `mergeVerdict`.
- To look at a surprising merge without writing a test: `node scripts/explain.mts <entrypoint.css> "<class list>" …` prints compiled declarations, class groups (generated and default), both merge results, and the oracle's verdict.
- Both packages sweep stale `tests/.tmp-*` directories in a Vitest `globalSetup` before workers start; keep scratch files under that prefix.
- Relative JavaScript requests can contain Windows separators: Tailwind's `loadModule` forwards them to enhanced-resolve, which uses Windows path normalization for drive-letter bases. The installed resolver was checked with nested and parent-directory requests using an emulated Windows filesystem; this is not a substitute for running generation, module-cache invalidation, and native watching on Windows. Do not infer a loader defect from backslashes alone.
- Tailwind's scanner (`@tailwindcss/oxide`) switches its ignore rules off for sources that sit inside gitignored paths (so `@source` can point into `node_modules`), and follows symlinks there. Both packages' temp test directories (`tests/.tmp-*`) are gitignored, so a scan rooted in one sees everything reachable from it: the Vite suite therefore nests copied fixtures one level below the temp directory and puts the `@tailwind-merge/vite` symlink at the temp directory's level (outside the Vite root), and the configurator's CLI `--prune` test scans a dedicated subdirectory. Any generated module inside a scanned directory counts as sources too — it is full of class-name literals.

Run `pnpm --filter @tailwind-merge/configurator test` and the matching `test:types` script for changes here, and the Vite suite for effects on generated behavior. Complete the repository-wide checks in [AGENTS.md](../AGENTS.md) before finalizing. CLI examples can be smoke-tested with `node packages/configurator/src/cli.ts` after building the workspace library.

## Remaining development work and revisit conditions

- Add a tested Tailwind version matrix before widening compatibility claims; declared peers are not coverage. The implementation baseline is 4.3.x, with unstable API drift a primary maintenance risk.
- Run the integration suites on Windows before claiming platform parity; current validation is on macOS and Linux, with only focused resolver checks for Windows paths.
- Keep absolute vanilla coverage in addition to differential conformance: default and generated configs can agree on the same bug. Review known divergence snapshots and the intentional-policy allowlist as the library evolves.
- Candidate upstream improvements are resolver/dependency hooks on `__unstable__loadDesignSystem` and exposed inline candidates on `compile()`. They would simplify the bundler loader adapter, dependency collection, and local safelist adapter; they are optional follow-ups, not prerequisites.
- Re-measure a specialized runtime only if usage pruning makes engine size dominant enough to justify duplicate semantics. The prior prebuilt-trie experiment doubled compressed config size to save less than a millisecond of one-time setup.
- Standalone CLI publication, other bundler adapters, and a shared runtime package follow demonstrated demand. The initial release strategy publishes the Vite wrapper with the configurator inlined; the core is not committed to remaining unpublished forever. Upstream integration discussions should be backed by real adoption and correctness evidence.

Release sequencing and the matching-library prerequisite belong in the [release guide](./release-workflow.md#publishing).
