# Next.js plugin development

Read this for work on `packages/next/`. User docs start in the [package README](../packages/next/README.md); discovery, generation, and refresh live in the [plugin core](./plugin-core.md), generator internals in the [configurator guide](./configurator.md), and the sibling Vite integration in the [Vite guide](./vite-plugin.md). Shared CI security rules remain in [library internals](./tailwind-merge-internals.md#ci-behavior-and-security).

## Goals and strategy

The same promise as the Vite plugin for Next.js apps: one config wrapper (`withTailwindMerge`) and one runtime import (`@tailwind-merge/next/runtime`), nothing written to disk, zero configuration for ordinary projects — with Turbopack and webpack, in the App Router and the Pages Router.

- Keep the plugin thin: the core decides what to serve and when; this package owns the Next.js config surface, the loader rules for both bundlers, dependency registration through the loader API, per-process state, logging, and failure policy.
- Keep development quiet and consistent: the served module depends only on the CSS configuration graph unless `prune.dev` is set, and every compilation environment (server components, server rendering, the browser) gets the same module from one generation.
- Make optimization failures safe: a failed source scan serves the full config with a warning; configuration-generation failures fail builds and keep the last good module in dev.

Boundaries: Next.js 16 and up (the plugin relies on `turbopack.rules` conditions, added in 16.0), the supported Tailwind line through `@tailwindcss/postcss` (an optional peer, like `@tailwindcss/vite` for the Vite plugin), one Tailwind root per app. Middleware/proxy, the edge runtime, custom servers, and Windows are untested.

## Architecture and invariants

| File in `packages/next/`                              | Responsibility                                                                                                                                                                                   |
| ----------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `src/index.ts`                                        | `withTailwindMerge`: merges the loader rules for Turbopack and webpack, `transpilePackages`, and the no-compiler-config warning into an object or function config.                               |
| `src/loader.ts`                                       | The loader both bundlers run on the package's own `runtime.mjs`: per-process project state around a core generation session, dependency registration, logging, and the dev/build failure policy. |
| `src/options.ts`                                      | The option types, prune-option resolution per mode, and the JSON-serializable loader options.                                                                                                    |
| `src/runtime.ts`                                      | Real fallback module, consumer type surface, and the legal-comment marker the Turbopack rule matches on.                                                                                         |
| `tsdown.config.ts`, `scripts/test-packed-package.mjs` | Build output and packed-consumer verification.                                                                                                                                                   |

How the module reaches the bundlers: neither Turbopack nor webpack offers virtual modules through the Next.js config, but both run webpack-style loaders. The plugin registers a rule on its own built `runtime.mjs` and the loader replaces that file's content with the generated module. Facts this rests on, verified with Next.js 16.3.4 and 16.3.5 (2026-09-13 spikes, reproduced in the suite):

- Turbopack matches rule conditions against real, project-relative paths, so a symlinked or linked install (`pnpm link`, a workspace) never contains `@tailwind-merge/next` in the matched path. The rule therefore keys on the file name (`*.mjs` glob plus a `runtime.mjs` path regex) and a `content` condition on the legal comment at the top of `src/runtime.ts`. Legal comments (`/*! */`) survive tsdown; ordinary comments do not — `tests/config.test.ts` checks the marker in `dist/runtime.mjs`. webpack gets an exact-path `test` against the realpath of the runtime file.
- Turbopack applies loader rules to code in `node_modules` only when the project has a `tsconfig.json` or `jsconfig.json`, even an empty one; without one, a bare `'*.mjs'` rule matches nothing there and the fallback file gets bundled silently. `withTailwindMerge` warns once per process when neither exists next to the working directory, every fixture ships a `jsconfig.json`, and the user docs say so. A bare `'foreign'` string condition also matched nothing in the spike; the plugin does not use it.
- Dev and build need different loader options (pruning, failure policy), while the Next.js config is evaluated for both commands alike (three times per Turbopack build in one process, twice per dev server, once per webpack build), so the mode is a rule condition: two Turbopack rules with the built-in `development`/`production` conditions, and `context.dev` in the webpack hook. Loader options must be plain JSON — Turbopack serializes them to Rust — hence `serializableLoaderOptions`.
- Both bundlers accept the loader as an absolute path to an ESM `.mjs` file, which the plugin derives from `import.meta.url`; no `exports` entry is needed. Both forward the loader's console output to the terminal; Turbopack does not surface `emitWarning`, so the loader logs through the console only.
- The loader runs once per compilation environment (three times per compile) in one process — webpack's own, or a Turbopack loader pool process that outlives compilations. The per-process project state coalesces concurrent runs into one generation; later runs `refresh()` the session, which reuses the module unless the CSS graph's modification times or the used classes changed. Both bundlers hash module content, so a regeneration with identical output changes nothing downstream.
- Loader context APIs (both bundlers unless noted): `rootContext` is the project directory even when `turbopack.root` is a parent; `getOptions()` returns nested JSON; `addDependency` and `addContextDependency` (directories, recursive) trigger re-runs; `addMissingDependency` works in webpack only — Turbopack accepts it without acting, which is why the recovery directories the core reports for missing imports are registered as context dependencies and cover creation.
- `transpilePackages` includes the package so the Pages Router's server bundle processes the runtime module instead of externalizing it; an externalized runtime would `require()` the fallback at request time while the browser ran the generated module. The Pages Router build test covers this.
- The generated module replaces a real file inside the package, so it imports `tailwind-merge` directly — resolution starts in the package's own directory. No internal `./tailwind-merge` subpath exists, unlike the Vite plugin's virtual module.
- `sideEffects` is `['./dist/runtime.mjs']`: the generated module calls `createTailwindMerge` at module scope, and marking the file side-effectful keeps any bundler from dropping the module as a pure re-export barrel. The spike showed the flag has no influence on rule matching.
- Failure policy: in build mode the session's `onError` throws, the loader rejects, and the build fails (both bundlers, verified with a missing explicit entrypoint); in dev it logs and serves the last good module, or `fallbackModuleCode` before the first success. Tailwind's own compilation of a broken entrypoint fails the page independently of the plugin, so the fallback-before-first-success test selects an explicit entrypoint the app does not import.
- What propagates after a regeneration is verified server-side (the next request renders with the new module) and for the served dev client chunk; browser-side Fast Refresh versus full reload is not automated.

## Testing

- The harness (`tests/helpers.ts`) drives real `next dev` and `next build` child processes through the CLI, in their own process group so `stop()` ends the CLI, the dev server it forks, and Turbopack's loader pool. Plugin options reach the fixture's `next.config.mjs` through the `TWM_OPTIONS` environment variable; `NODE_ENV` is set per command (Vitest's `test` would make Next.js warn). Dev servers get a free port and are ready once the index route answers 200.
- Fixtures are copied to `tests/.tmp-*` one level below the temp directory with the `@tailwind-merge/next` symlink at the temp level, like the Vite suite (the [oxide gitignore trap](./configurator.md#debugging-and-validation)). Turbopack's inferred root is the repository root (nearest lockfile), which keeps the symlink target inside it. The app fixture's CSS uses `source('.')` because the gitignored copy turns oxide's ignore rules off and `.next` would be scanned as sources; the Pages fixture leaves automatic detection on to cover the `rootContext` base. Fixture comments must not spell out class names — the scanner reads comments, and a `p-2`/`p-4` in a comment once made pruning keep the padding group.
- The loader executes inside the Next.js processes, so the coverage report shows `src/loader.ts` at zero — its behavior is covered through the served pages and build output, not through instrumentation. The Next.js processes resolve through real `node_modules`, so no source aliases apply: the global setup builds this package's `dist/` every run and the library's only when missing (a stale library dist is a `pnpm --filter tailwind-merge build` away). In-process tests (`config.test.ts`) use the Vitest aliases to the library source like the other packages.
- Pruning is asserted on production bundles (an unused class group's literal, `forced-color-adjust`, is absent from the client chunks) and on server-rendered output (unused padding classes pass through `twMerge` unmerged), never on dev bundles: without production tree shaking they carry the whole tailwind-merge library, whose default config spells every group, so an absence probe cannot work there.
- Suite: `config.test.ts` (config merging for object and function configs, rule conditions against the install layouts, prune-option resolution, runtime-surface parity with the core's fallback), `build.test.ts` (both bundlers: pruned prerender plus client chunks plus the log line, `prune: false`, a missing explicit entrypoint failing the build, the Pages Router server bundle; the consumer-types fixture), `dev.test.ts` (both bundlers: generated module on server and browser with surface parity and a theme edit, broken theme keeping the last good module and recovering, `prune.dev` following class usage; plus the fallback-before-first-success and no-Tailwind-root cases). Expect about two minutes; the package timeout is 120 s per test.
- Remaining coverage: middleware/edge, custom servers, Windows, Turbopack's filesystem cache (`turbopackFileSystemCacheForBuild`) honoring the registered dependencies, browser-side refresh behavior, linked-package layouts beyond the workspace symlink, and dynamic routes at `next start` (prerendered pages cover the bundled module today).

Run `pnpm --filter @tailwind-merge/next test` and `test:types` for plugin changes, then the repo-wide checks.

## Build and packaging

`packages/next` builds with tsdown like the Vite package: ESM-only, one bundle and one declaration file per entry (`index`, `loader`, `runtime`), declaration maps on, `deps.onlyBundle: []` and `deps.onlyImport` guarding the import surface (`next` appears in declarations only).

- The workspace `exports` already point at `dist/` — there is no `publishConfig.exports` swap — because the fixtures' Next.js processes load the package through plain Node resolution. The test global setup builds it; `tests/fixtures/consumer-types` maps the package names to `src/` for its type check.
- `index` must stay light and import nothing the loader needs at runtime, so rolldown emits no shared chunk between the two entries and `next.config` loads without touching the Tailwind compiler. The declarations do share an `options-<hash>.d.mts` chunk (both entries reference the option types); the packed gate normalizes the hash.
- Runtime dependencies match the Vite plugin's (`tailwind-merge`, `@tailwindcss/node`, `@tailwindcss/oxide`, `enhanced-resolve`, `postcss`); peers are `next` (`^16.0.0`), `tailwindcss`, and the optional `@tailwindcss/postcss`, the Tailwind ones tilde-pinned to the supported line. Next.js allows Node 20.9; this repository's toolchain needs 22.18, so the plugin's own Node floor is untested below that.
- `pnpm --filter @tailwind-merge/next test:exports` (`scripts/test-packed-package.mjs`) packs with pnpm, asserts the tarball's file list and manifest (exports, `sideEffects`, exact dependency set, no `workspace:` protocols), moves the extracted package into a temp-directory consumer with Next.js, React, Tailwind, and the library linked next to it, imports both subpaths and checks the config the plugin produces (loader path exists, webpack rule matches the installed runtime), runs a real `next build --webpack` of a consumer app and checks the prerendered merge and pruning, and type-checks the consumer-types fixture against the bundled declarations. The consumer build uses webpack because Turbopack refuses to resolve files outside the project root it infers, and the consumer's dependencies are links into the workspace; the vitest suite covers Turbopack. Requires this package's and the library's `build` first.
- `test:library-release` runs the shared `scripts/check-library-release.mjs` with `--sources ../configurator/src ../plugin-core/src src`, as the Vite package does with its own source list.
- The README's relative links are pinned by the `version` lifecycle and the dev-release stamp exactly like the Vite package's.

## Release boundaries

The versioned surface is `withTailwindMerge`'s options and the `@tailwind-merge/next/runtime` exports; the loader module, the rule conditions, and the generated representation are internal. The first stable release is `0.1.0`; until then every `main` push publishes a dev build through the trusted publisher the manual bootstrap publish created — that bootstrap and the sequencing against the library and the Vite plugin are in the [release guide](./release-workflow.md#first-nextjs-release).
